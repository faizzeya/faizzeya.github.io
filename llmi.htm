Foundations

Generation is a loop: score, sample, append

Pseudocode

logits, kv = prefill(prompt)
tok = sample(logits)
while tok != EOS and n < max_new:
    emit(tok)
    logits, kv = decode_step(tok, kv)
    tok = sample(logits / T)

Each iteration depends on the previous token, so steps cannot run in parallel for one sequence.

Sampling turns logits into one token

MethodWhat it does
GreedyAlways pick the most likely token
Temperature TT < 1 sharpens, T > 1 flattens
Top-kSample from the k most likely tokens
Top-pSmallest set whose probability ≥ p
Min-pDrop tokens below p × the top probability

Sampling is cheap; the forward pass that produces the logits is the expensive part.

Point out the data dependency: token n+1 needs token n. That is why we cannot parallelize decode within a sequence, and why later tricks like batching and speculative decoding exist. Sampling choices change output quality, not speed.

This is the single most important table in the deck. Prefill looks like training: large matrix multiplies that saturate tensor cores. Decode looks nothing like training: tiny amounts of math per byte read. Optimizations that help one phase often do nothing, or harm, the other.

Queueing plus prefill. How long until something appears.

Also TPOT. Gap between streamed tokens; set by decode.

Define each metric precisely, since students will use them in the lab. Goodput is the honest metric: throughput only counts if the requests behind it met the latency promise. Mention that average latency hides the users who had a bad experience.

The memory wall

Why decode speed is set by bytes moved, not FLOPs — and why the KV cache becomes the central resource

Transition: we have the vocabulary; now we build the mental model that explains almost every optimization that follows.

The memory wall

The roofline model explains decode

intensity = FLOPs ÷ bytes moved

H100 SXM: ~989 TFLOPS dense BF16 vs 3.35 TB/s HBM → the ridge is at ≈ 295 FLOP/byte.

Decode reads each 2-byte weight once per step and does ~2 FLOPs with it per sequence → intensity ≈ batch size.

At batch 1 the GPU reaches about 0.3% of peak compute. Prefill of a long prompt sits on the flat roof.

Derive the decode intensity live on the board: each weight is 2 bytes in BF16 and contributes one multiply and one add per sequence in the batch, so intensity is about one FLOP per byte per sequence. At batch 1 we use roughly 3.35 TFLOPS out of 989, about a third of a percent. Batching moves us up the slope for free until we hit the ridge. Peak figures are NVIDIA H100 SXM datasheet values.

Note the last two rows: quantizing the 70B model to 4 bits on one GPU matches the bandwidth bound of four GPUs in BF16. This is why quantization is a speed optimization, not only a memory one.

The memory wall

The KV cache: remember, don’t recompute

Attention for a new token needs the keys and values of every earlier token, in every layer.

Recomputing them each step makes generating n tokens cost O(n²) projection work.

So we compute them once — in prefill for the prompt, then one row per decode step — and keep them in GPU memory.

The price: memory that grows with layers × context length × batch size.

The new token’s query is compared with every cached key, and the result weights every cached value. Only the new token’s K and V are computed this step. GQA is the reason the Llama 3 numbers on the previous slide are manageable: 32 or 64 query heads, but only 8 KV heads. MLA is DeepSeek’s approach and is now copied by others. KV quantization and eviction are knobs the operator controls, with eviction trading accuracy on long-range recall.

03

Serving systems

Packing many users onto one GPU: batching, paging, caching and splitting the work

The roofline told us decode wastes compute at small batch. Serving systems exist to build big, efficient batches out of many unpredictable users.

Serving systems

Static vs continuous batching

Static: wait for the slowest

Gray = idle slot. New requests queue until the whole batch finishes.

Continuous: refill every step

Orange = new requests admitted the moment a slot frees up.

Scheduling at the granularity of one decode step (Orca, OSDI 2022) keeps the batch full. It is now standard in every serious engine and often the single largest throughput win.

Each bar is one request slot over time. With static batching, short answers leave their slot idle while the longest answer finishes, and queued users wait. Continuous, or in-flight, batching re-forms the batch after every iteration, so throughput rises and queueing time drops.

Serving systems

PagedAttention: virtual memory for the KV cache

Problem: reserving one contiguous slab per request for its maximum length wastes memory to fragmentation and over-reservation — the vLLM paper measured 60–80% waste in earlier systems.

Idea: split the cache into fixed-size blocks (e.g. 16 tokens) placed anywhere in memory, tracked by a per-sequence block table — like OS pages.

Bonus: sequences can share blocks with copy-on-write, so parallel samples and common prefixes cost memory once.

Draw the analogy explicitly: logical pages, physical frames, and a page table. vLLM’s 2023 SOSP paper reported 60 to 80 percent KV memory waste in prior systems and near-zero waste with paging; more free memory means larger batches, which, from the roofline, means more throughput.

How

Hash KV blocks by their token content (vLLM) or keep a radix tree of prefixes (SGLang’s RadixAttention).

Why it matters

Chat history, RAG documents, few-shot examples and agent loops all resend long shared prefixes.

Design tip

Put stable content first in prompts; route requests to the replica that holds their prefix.

This is what commercial “prompt caching” features expose to API users, usually as a discount on cached input tokens. A cache hit removes most of the prefill, so TTFT drops sharply. Ask students why putting a timestamp at the start of a system prompt would destroy the hit rate.

Serving systems

Chunked prefill: stop long prompts from freezing everyone

Without chunking — a 32K-token prompt arrives

Every decoding user stalls for the whole prefill → an inter-token latency spike.

With chunking — fixed token budget per step

Blue = prefill chunk, orange = decode tokens. Each step mixes both, so streams keep flowing.

Introduced as Sarathi-Serve (OSDI 2024). Tuning knob: the per-step token budget — larger favors TTFT and throughput, smaller favors smooth streaming.

Each block is one engine iteration. A large prefill in a single iteration holds every other user hostage. Chunked prefill slices the prompt into pieces of, say, 512 to 2,048 tokens and piggybacks the decode tokens of other requests on each slice. The prefill also fills otherwise-idle compute in decode-heavy batches.

Serving systems

Disaggregation: prefill and decode on separate GPUs

Router

KV-aware, load-aware

Prefill pool

Compute-bound. Big batches of prompt tokens; compute-dense GPUs.

KV cache

RDMA / NVLink

Decode pool

Bandwidth-bound. Many concurrent streams; HBM-rich GPUs.

Gains

No prefill–decode interference; each pool scales and is parallelized for its own phase. Published benchmarks report roughly 2–3× throughput, workload-dependent.

Costs

KV transfer over a fast fabric, more moving parts, and a prefill:decode ratio to tune. Rarely worth it on a single small server.

Where

vLLM, SGLang and TensorRT-LLM support it; NVIDIA Dynamo orchestrates the pools and routing.

DistServe (OSDI 2024) and Splitwise made the academic case in 2024; by 2026 every major stack supports it. The key insight goes back to the phases table: the two halves want different hardware and different batch shapes, so stop forcing them onto the same GPU.

Kernels & numerics

The same math with fewer bytes and fewer trips to memory

Serving systems decide what runs together; kernels and number formats decide how fast each step runs.

Kernels & numerics

FlashAttention: IO-aware, exact attention

Naive attention

S = QKᵀ

→ HBM →

P = softmax(S)

→ HBM →

PV

Writes and re-reads the full N × N score matrix in slow GPU memory. Memory traffic grows with N², so long contexts become bandwidth-bound.

FlashAttention

tile Q, K, V

→ on-chip SRAM →

online softmax

Processes blocks that fit in fast on-chip memory and rescales the softmax as it goes. The N × N matrix is never stored. Same result, linear memory, far less HBM traffic.

VersionWhat it added
FlashAttention (2022)Tiling + online softmax; exact attention with O(N) memory
FlashAttention-2 (2023)Better work partitioning across GPU thread blocks and warps
FlashAttention-3 (2024)Hopper features: asynchronous data movement, FP8
Flash-Decoding, FlashInferSplit the KV cache across blocks so decode with long context stays parallel
Key word: IO-aware. FlashAttention does the same number of FLOPs, in fact slightly more, but moves far fewer bytes, which is what matters on a bandwidth-bound device. Every major engine uses Flash-style kernels by default today, so this is table stakes rather than a knob.

Kernels & numerics

Quantization: fewer bytes per weight

A 70B-parameter model’s weights

BF16

140 GB · ≥ 2 GPUs

FP8

70 GB · 1× 80 GB GPU, little room for KV

4-bit

35 GB · fits one 48 GB GPU

W4A16 (weight-only)

4-bit weights, 16-bit math. Speeds up memory-bound decode; little help for prefill.

W8A8 (INT8 / FP8)

Weights and activations in 8 bits. Faster tensor-core math too, so prefill gains as well.

W4A4 (FP4)

Both in 4-bit floats on Blackwell tensor cores. Highest speed; needs careful calibration.

The naming convention WxAy means x-bit weights and y-bit activations. Weight-only quantization reduces bytes, which helps decode. Quantizing activations as well lets the matrix multiply itself run in low precision, which helps compute-bound prefill. Always re-run your quality evaluations after quantizing.

Rule of thumb: start with FP8, move to 4-bit when memory-bound — and keep sensitive layers in higher precision if evaluations drop.

These are post-training methods; no retraining is needed, only a small calibration set. GPTQ uses approximate second-order information to compensate rounding error; AWQ scales the small fraction of weight channels that matter most; SmoothQuant moves the difficulty of quantizing activations into the weights. Some recent models ship natively in FP8 or 4-bit, avoiding the conversion step.

Kernels & numerics

Small batches drown in overhead

A decode step at small batch is hundreds of tiny GPU kernels. Launching them from the CPU, and writing intermediates between them, can take longer than the math itself.

🔧

Kernel fusion

Merge steps (QKV projection, norm + matmul, fused MoE) so intermediates never leave the chip.

▶

CUDA Graphs

Record a decode step once, replay it with one launch per step instead of hundreds.

</>

Compilers

torch.compile and TensorRT generate fused, shape-specialized kernels automatically.

⏱

Overlap scheduling

The CPU prepares the next batch while the GPU runs the current one, hiding scheduler time.

This is the slide that explains why a naive Hugging Face generate loop is so much slower than vLLM or SGLang on the same GPU, even before batching. Much of modern engine work is removing CPU-side overhead.

Smarter decoding

Getting more than one token out of each expensive forward pass

Decode at small batch leaves compute idle. Speculative decoding spends that idle compute to cut latency, without changing the output distribution.

Smarter decoding

Result: 4 tokens for one target pass instead of 4 sequential passes.

Why it works

Verifying k tokens costs about the same as generating one: decode is memory-bound, so the extra math is nearly free.

Why it is lossless

A rejection-sampling rule makes the output distribution exactly the target model’s (Leviathan et al., 2023).

Walk through the example. The draft guesses four tokens; the target checks them in one pass and agrees with the first three. At the first disagreement, we keep the target’s own token, so every round produces at least one token. With greedy decoding it is easy to see why output is identical; with sampling, the accept-reject rule guarantees the same distribution.

Smarter decoding

How much does speculation buy?

E[tokens per pass] = (1 − α^(k+1)) ÷ (1 − α)

α = probability the target accepts a draft token
k = draft length

Real speedup is lower: drafting and verification cost time too. Long drafts only pay off when α is high.

At large batch the GPU is already busy, so gains shrink — speculation is mainly a latency tool.

Derivation: the number of accepted tokens is geometric, truncated at k, plus one bonus token from the target. When one GPU is not enough: splitting models, experts and hardware choices

Frontier models do not fit on one accelerator. This part covers how the work is split and what that costs in communication.

👥

Default recipe: TP inside a node, replicas across nodes, EP for MoE.

Recall the decode bound: splitting weights over four GPUs with tensor parallelism quadruples the aggregate memory bandwidth, which is why TP cuts per-token latency. The price is an all-reduce in every layer, so it only works over very fast interconnect. Replicas are embarrassingly parallel and should be the first scaling step for throughput.

A router sends each token to a few experts out of many. Compute scales with active parameters; memory scales with total.

Small batches: few experts are touched, but you still pay to hold them all.

Large batches: nearly every expert is used, so intensity recovers — MoE serving wants big batches and expert parallelism.

New problems: load imbalance across experts and all-to-all communication every MoE layer.

Most frontier open models are now mixture-of-experts. DeepSeek-V3 is a good teaching example because its numbers are public: 671 billion total parameters, 37 billion activated per token. Ask the class: what does that do to the roofline intensity of decode at batch 1 versus batch 256?

All three main GPU engines expose an OpenAI-compatible HTTP API, so switching between them is usually a deployment change, not an application change. Benchmarks change monthly, so teach students to benchmark on their own workload rather than trusting leaderboards.

In practice

Reasoning models and agents shift the load

“Thinking” models generate long hidden chains of thought; agents call the model again and again with a growing context. Both stress the exact resources we have discussed.

Decode-heavy

Thousands of output tokens per answer: speculative decoding and low-precision weights pay off most.

KV-heavy

Long sequences grow the cache; fewer users fit, so GQA/MLA and FP8 KV matter more.

Prefix-heavy

Agent loops resend tools, instructions and history: prefix caching becomes essential.

Parallel sampling

Best-of-n and self-consistency share one prompt: copy-on-write KV blocks make it cheap.

Test-time compute means quality now scales with inference spend, not only with model size. That turns every optimization in this lecture into a quality lever: if tokens are cheaper, you can afford to let the model think longer or sample more candidates.

In practice

A tuning playbook, in order

01

Define SLOs (P99 TTFT, P99 ITL) and load-test with realistic prompt and output lengths.

05

Tune batch limits and the chunked-prefill token budget against the SLO.

02

Use a modern engine. Continuous batching, paged KV and Flash kernels are table stakes.

06

Add speculative decoding for latency-sensitive, low-batch traffic; measure acceptance.

03

Quantize: FP8 first; 4-bit when memory-bound and evaluations still pass.

07

Scale out: replicas first, TP within a node, disaggregate at multi-node scale.

04

Cache prefixes: enable prefix caching and put stable content first in prompts.

08

Re-check quality after every change; speed that breaks answers is not a win.

Change one thing at a time, and keep the benchmark that proved it.

The order matters: cheapest and safest changes first, architectural changes last. The grid reads down each column, one through four, then five through eight.

Key takeaways

Six ideas to keep

Two phases

Prefill is compute-bound; decode is memory-bandwidth-bound.

KV cache rules

At long context or high concurrency it, not the weights, limits how many users fit.

Batch smartly

Continuous batching, paging and prefix caching turn idle compute into throughput.

Fewer bytes

Quantization speeds decode almost in proportion to the bytes it removes.

Spare compute buys lower latency with identical outputs — if drafts are accepted.

Measure

Every trick is workload-dependent. Benchmark against SLOs, on your own traffic.

Close by connecting back to the roofline: nearly every technique either raises arithmetic intensity, by batching and speculation, or reduces bytes, by quantization, paging and KV compression. Invite questions, then introduce the lab.
